# NurtureLink: PLAN.md

> Nurture Lives, Linking Hearts

Responsive, installable (PWA) web app for pregnant patients and healthcare providers. Monitoring and screening prototype only. **Not a diagnostic device.**

## 1. How We Work (manual workflow)

Claude has **no access** to the GitHub repo or the Supabase project. The workflow is:

1. The user starts a session by attaching `PLAN.md`, `CLAUDE.md`, and (when changing existing code) the current files or a zip of the repo without `node_modules`.
2. Claude outputs **complete files** with their exact repo paths, plus a numbered **Manual Steps** list.
3. The user uploads files to GitHub (web upload, GitHub Desktop, or git) and runs SQL in the **Supabase SQL Editor**.
4. The user tests and reports back exact errors or screenshots (no real data in them).
5. Claude updates the Progress Log and Environment State.

Consequences:

- Claude never guesses what is already in the repo or database. If a file or table state is needed and not provided, Claude asks for it.
- SQL is delivered as numbered files in `supabase/migrations/`, run **in order** by the user in the SQL Editor, and also kept in the repo as the record.
- Where Claude has a sandbox, it builds and tests the front end there before delivering, and says what it could and could not verify. Claude cannot reach Supabase from the sandbox, so database behavior is verified by the user.
- GitHub web upload handles about 100 files per batch and cannot extract zips. Claude groups deliverables so each step is a manageable upload and says which folders to drag in. Unzip locally first if Claude delivers a zip. The web uploader may skip hidden folders such as `.github`; create those files with **Add file > Create new file** if needed.

## 2. Hard Rules (never break)

1. **No real patient data** in the repo, commits, seeds, screenshots or chats. Synthetic data only.
2. **Only the Supabase publishable (public) key** goes in the repo or build, through a GitHub repository variable. `sb_secret_...` and legacy `service_role` keys never go in any file, chat or the front end.
3. **Roles are set server-side.** The client never chooses or sends its own role.
4. **Access control is enforced by RLS plus minimal grants**, never by front-end checks alone. GitHub Pages cannot protect anything.
5. **No hard-coded UI text.** Every string uses an i18n key with both `en` and `fil` entries.
6. **Every reading screen shows the disclaimer:** monitoring and screening, not diagnosis.
7. **Alert colors (red, amber, green) stay separate from brand coral.** Status is never shown by color alone.
8. **Providers cannot self-register.** Accounts come from an admin or an invite code.
9. **Claude never runs SQL for the user.** The user reviews each SQL file before running it.
10. **Nothing is exposed by default.** New tables are not auto-exposed. Every table and function gets explicit, minimal grants. `anon` has no table privileges.

## 4. Supabase Access Model

Two locks, both required:

1. **Grants:** the role must have privileges on the table or function. The project is set up so new tables are not exposed automatically, and migration `000_project_hardening.sql` removes default privileges from `anon` and `authenticated` (and the built-in "everyone can run new functions" default) so it is safe regardless of how the project options were set at creation.
2. **RLS policies:** decide which rows that role can read or change.

Also: helper functions are `SECURITY DEFINER` with a fixed `search_path`, with `EXECUTE` revoked from `PUBLIC` and `anon` and granted only where needed. An event trigger (or explicit `enable row level security` in each migration) ensures every new table has RLS on.

## 5. Roles and Access

- **Patient:** reads and writes only their own data.
- **Provider:** reads only patients assigned to them. Only providers reach validation, reports and audit log.
- **Admin:** the project owner. Creates provider invites and manages consent documents through the SQL Editor (never from the client).
- Every provider read of patient data is written to the audit log.

## 7. Features by Tab

**Patient app**

- **Home:** status (green/amber/red), latest fetal heart rate with confidence, maternal HR, SpO2, temperature, "Check now", device and battery status, next appointment, SOS.
- **Monitor:** trends (day/week/month), check history with signal quality, "adjust belt" guidance, manual entry when offline.
- **Alerts:** list with severity, contact provider, acknowledge, SOS history.
- **Care:** book/reschedule/cancel appointments, telemedicine (chat + video link), consult history.
- **Profile:** pregnancy details (auto gestational age and trimester), health timeline, device pairing, manual and videos, consent and privacy controls, language, logout.

**Provider dashboard**

- **Overview:** triage by priority, SOS banner, unacknowledged alerts, missed checks.
- **Patients:** search/filter (trimester, risk, last check), add/assign, eligibility checklist.
- **Patient detail:** profile and risk flags, FHR trend with maternal overlay, vitals, alert history, notes, device status, wear-schedule editor.
- **Alerts:** queue, acknowledge, record action taken (call / telemedicine / refer to clinic).
- **Consults:** calendar, requests, notes.
- **Validation:** belt vs Doppler pairs, percent error, MAE, detection rate by gestational age, Bland-Altman, OB and pediatrician sign-off, per-session consent.
- **Reports:** anonymized summaries, CSV/PDF export.
- **Settings:** alert thresholds, wear protocol, audit log, account.

## 9. Core Logic

- **Maternal pickup filter:** reject belt reading if within a few bpm of the wrist band's heart rate.
- **Alert triggers:** sustained FHR outside range (default 110-160 bpm, **pending medical officer confirmation**, editable in Settings), repeated signal loss, low SpO2, fever, SOS.
- **Alert creation:** database function on insert into readings; delivered via Realtime.
- **Wear schedule:** provider sets check windows per patient (morning/afternoon/evening).
- **Offline-first:** store readings locally, sync on reconnect without duplicates.
- **Demo Mode:** seeded data plus simulated device stream. The provider lock fully applies only in Live Mode, and the demo says so.
