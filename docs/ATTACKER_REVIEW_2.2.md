# Attacker review, step 2.2 (grants 004 and row rules 005)

**Attacker model:** a person with a normal patient account (valid JWT, role `authenticated`) who calls the Data API (PostgREST), GraphQL, Realtime and RPC directly, ignoring the app. A second attacker with no account (`anon`) is covered too.

**Goal of the attacker:** read another patient's data, read provider-only data, become a provider or admin, or change recorded clinical data.

**How to read the table:** "Test" names the check in `supabase/tests/access_tests.sql` that fails if the defence is removed (eight representative defences were removed one at a time in a sandbox, for example the audit_log grant, the role column grant, a policy and RLS itself, and every time the matching tests turned red).

## 1. Result in one paragraph

No way was found to read another patient's data, or provider-only data, from a patient account. Four gaps were identified while designing and closed in the SQL before delivery (section 3). Eight residual risks remain; none leaks patient data, and they are listed in section 4 with what to do about each.

## 3. Gaps closed in the SQL (found at design time, before delivery)

1. **Default grants from before 000.** Tables created before 000 ran carry `TRUNCATE`, `REFERENCES`, `TRIGGER`, `MAINTAIN` for anon and authenticated (seen in your diagnostic). TRUNCATE ignores RLS: any patient could have wiped a table through the API if the Data API ever exposed it. Fix: 004 starts with `revoke all on all tables and sequences in schema public from anon, authenticated`, and a test fails if any table-level privilege of that kind returns.
2. **Stray policies.** A policy created by hand in the dashboard (for example "enable read access for all users") would survive and silently open a table, because policies are combined with OR. Fix: 005 drops every existing policy in `public` before creating its own, so the result is always exactly what the file says. A test fails if any policy targets anon or PUBLIC.
3. **Threshold edits by providers could silently change patient safety rules.** Fix: `guard_threshold_update` trigger (in 005) stamps `updated_by`, resets `is_confirmed` to false when a limit changes, and writes an audit row; `is_confirmed` itself is not writable from the client.
4. **Patient-written severity and timestamps.** `alerts.severity` (update), `consent_records.accepted_at` and `belt_readings.created_at` (insert) are deliberately left out of the column grants so the server always sets them, instead of trusting the client.

## 4. Residual risks (not fixed on purpose; your decision)

| Risk | Why it remains | Suggested handling |
|---|---|---|
| **Invite code guessing.** Codes have 64 random bits, so guessing is not realistic, but there is no rate limit on the RPC | Supabase rate limits cover Auth, not RPC | Keep codes long and short-lived (default 7 days); delete used and expired invites; consider a failed-attempt counter later |
| **Flooding.** A patient can insert unlimited readings, SOS alerts or devices | Needed for normal operation | No rate limit exists at the database level; add size limits and a daily cap trigger in Phase 3 if abuse appears |
| **`alerts.details` and free-text fields are patient-written JSON/text** (SOS details, device label, conditions, `deletion_requests.note`) | Needed | The app must render them as text only (React does by default). Never use `dangerouslySetInnerHTML`. Provider screens show them, so this is a stored-XSS target |
| **Any provider can edit the global alert thresholds** (they are not per patient) | The spec allows providers to edit thresholds; global limits are the design in 001 | The guard trigger resets confirmation and logs it. If you prefer admin-only, remove the `alert_thresholds` update grant and policy (one line each) |
| **A provider who is assigned can read `date_of_birth`, `display_name`, language of the patient** | "Basic profile" is table-wide for a visible row | Acceptable clinically. If you want less, move DOB to a separate table |
| **Two-person validation sign-off.** The database stops one provider signing both OB and pediatrician slots on one pair, but a person can still hold two provider accounts | Identity beyond an account is not something SQL can check | Admin controls who gets provider invites; log review |
| **A patient does not yet get a "seen" or acknowledge action on alerts.** The spec says patients may update their own rows, but a patient updating `status` would let them close a critical alert before a provider sees it | Left out deliberately | Needs a separate column (for example `seen_by_patient_at`); decision pending, see Open items |
| **Supabase-owned `rls_auto_enable()` function** is anon-callable in some projects | Owned by Supabase, not changeable here | Test prints it as INFO; it can only act inside Supabase's event trigger |
